## 욕구조사를 하기 전에, 설문지를 먼저 테스트할 수 있다면

프로그램 기획 회의에서 늘 같은 장면이 반복됩니다.

"어르신들 대상으로 새 프로그램 6개 후보가 있는데, 어떤 걸 하면 좋을까요?"
"일단 욕구조사를 돌려봅시다."

그런데 설문지를 만드는 순간부터 막힙니다. 어떤 보기를 넣어야 할지, 참여를 막는 이유를 어떻게 물어야 할지,
주관식을 넣으면 답이 나올지. 결국 담당자 경험에 의존해 문항을 만들고, 200부를 인쇄해서 돌린 다음
집계 단계에서 이런 걸 깨닫습니다.

- "이 문항은 90%가 같은 보기를 골랐네. 물어볼 필요가 없었구나."
- "기타 응답에 '차량 지원'이 계속 나오는데, 이걸 보기에 넣었어야 했다."
- "참여 의향은 높은데 왜 안 오는지는 못 물어봤네."

한 번 돌린 조사는 되돌릴 수 없습니다. 소규모 기관은 FGI나 파일럿 조사에 쓸 시간과 예산도 넉넉하지 않습니다.

그래서 **실제 주민에게 묻기 전에 설문지를 먼저 점검하는 도구**를 만들었습니다.

- 저장소: https://github.com/kijung4290/virtual-survey-lab
- 이름: Synthetic Client Survey Lab

## 무엇을 하는 도구인가

공개 통계와 합성 데이터로 **가상 이용자 패널(Synthetic Clients)** 수백 명을 만들고,
실제 조사에 쓸 설문지를 **그 패널에게 먼저 실행**합니다. 그리고 결과에서 이런 것을 찾습니다.

- 어떤 프로그램 후보가 상대적으로 반응이 높은가
- 독거 / 부부 / 자녀동거 가구에서 선호가 어떻게 갈리는가
- 참여를 막는 이유로 무엇이 반복해서 나오는가
- 응답이 한쪽으로 쏠리는 문항은 없는가 (= 물어볼 필요가 없는 문항)
- 주관식에서 **내가 보기에 넣지 않은 답**이 나오는가

여기서 중요한 건 이 도구의 위치입니다. 제가 가장 신경 쓴 원칙이 하나 있습니다.

> **Synthetic Clients는 실제 이용자를 대신하기 위한 것이 아니라,
> 실제 이용자에게 더 좋은 질문을 하기 위한 사전 실험 도구입니다.**

AI가 만든 응답을 "주민들은 이렇게 생각한다"로 쓰는 순간 이 도구는 해로워집니다.
그래서 모든 결과 화면에 다음 문구를 고정해 두었고, 지울 수 없게 했습니다.

> 이 결과는 AI와 합성 페르소나를 이용한 사전 시뮬레이션입니다.
> 실제 이용자·지역주민의 욕구조사를 대체하지 않습니다.

## 전체 흐름

```
프로그램 아이디어
      │
      ├─ ① 가상 이용자 패널 만들기      통계 비율 입력 또는 합성 데이터 CSV
      ├─ ② 설문지 작성                 실제 조사에 쓸 문항 그대로
      ├─ ③ 가상 패널에게 설문 실행      1명 = 독립 응답자 1명
      ├─ ④ 결과 분석                   세그먼트 차이 · 참여장벽 · 쏠린 문항
      │        ↓
      │   실제 설문지 보완 → 실제 주민 조사 실시
      │        ↓
      └─ ⑤ 실제 결과와 비교            %p 차이 · 순위 차 · MAE · 순위상관
```

### ① 가상 이용자 패널 만들기

두 가지 방법이 있습니다.

**방법 1. 통계 비율 입력.** "65~74세 45% / 75~84세 40% / 85세 이상 15%",
"독거 38% / 부부 42% / 자녀동거 20%" 처럼 알고 있는 분포를 넣으면 그 비율에 맞는 패널이 만들어집니다.

**방법 2. 합성 데이터 CSV 가져오기.** NVIDIA가 공개한 Nemotron-Personas-Korea 같은
합성 페르소나 데이터를 쓸 수 있습니다. Parquet 파일을 CSV로 바꾸는 스크립트를 함께 넣어 뒀습니다.

```bash
npm run personas:csv -- data/private/nemotron-korea.parquet --min-age 65 --limit 300 --seed 42
```

이때 `gender → sex`, `region → province` 처럼 흔한 컬럼명은 자동으로 표준 속성에 매핑되고,
**이름·연락처 같은 개인정보 의심 컬럼은 변환 단계에서 아예 제외**됩니다.

![스크린샷: 분포 입력 화면 또는 CSV 컬럼 매핑 화면](./images/02-clients.png)

### ② 설문지 작성

단일선택 / 복수선택 / 5점척도 / 숫자 / 주관식을 지원하고, **조건부 문항**도 됩니다.
"Q2 참여의향이 2점 이하일 때만 Q7(불참 이유)을 물어본다" 같은 분기를 그대로 만들 수 있습니다.

실제 조사에서 쓸 문항을 **그대로** 넣는 것이 핵심입니다. 문항을 시뮬레이션용으로 다듬으면 테스트 의미가 없습니다.

### ③ 가상 패널에게 설문 실행

가상 이용자 한 명이 응답자 한 명입니다. **각자 자기 페르소나 정보만 받고, 다른 응답자의 답은 보지 못합니다.**
300명이면 300번 독립 호출이 일어납니다.

실행 전에 예상 호출 수를 반드시 보여주고, 사용자가 확인 체크박스를 눌러야 시작됩니다.

```
대상 응답자: 300명
설문 실행: 3회
예상 API 호출: 900회
```

![스크린샷: 실행 설정 + 예상 호출 수 확인 화면](./images/03-run.png)

### ④ 결과 분석

문항별 비율·순위, 척도 평균/표준편차, 주관식 키워드, 그리고 **세그먼트 교차 분석**이 나옵니다.

```
병원동행 선호율
독거        41%
부부        24%
자녀동거    18%
```

제가 제일 쓸모 있다고 느낀 건 **문항 검토 제안**입니다. 한 보기에 70% 이상 몰리거나
아무도 고르지 않은 보기가 있으면 경고를 띄웁니다. 실제 설문지에서 그 보기를 고치라는 신호입니다.

![스크린샷: 결과 분석 — 선호도 차트 + 세그먼트 표](./images/04-analysis.png)

### ⑤ 실제 조사 결과와 비교

실제 조사를 마친 뒤 익명화된 CSV를 올리면 두 결과를 나란히 비교합니다.

```
Q1. 가장 참여하고 싶은 프로그램
                 Synthetic   실제    차이
병원동행             31%      26%    +5%p
스마트폰교육         22%      30%    -8%p
건강걷기             19%      18%    +1%p
```

%p 차이, 순위 차이, 평균 절대 오차(MAE), Spearman 순위 상관을 계산하고 해석 문구를 자동 생성합니다.
단, **해석문은 LLM이 아니라 규칙 기반**으로 만듭니다. AI에게 해석을 맡기면 "이동 불편 때문에
병원동행 선호가 높았다" 같은 인과관계를 자신 있게 주장하기 때문입니다. 이 도구는 차이를 보여주는 데까지만 합니다.

![스크린샷: Synthetic vs 실제 비교 리포트](./images/05-comparison.png)

## 실제로 어떻게 답하는지

Gemini로 3명을 돌린 결과입니다. 페르소나 속성이 응답에 반영되는 걸 볼 수 있습니다.

```
SC-0001  82세 여성 · 독거 · 이동불편 중간 · 사회적 접촉 낮음
  선호: 소규모 식사모임 (참여의향 4점)
  이유: "혼자 살고 있어서 다른 사람들과 만나 대화를 나누며 식사할 기회가 생겼으면 좋겠습니다."
  장벽: 건강 문제 / 필요 지원: 건강관리, 말벗·정서, 이동·차량

SC-0003  81세 여성 · 자녀동거 · 이동불편 중간
  선호: 소규모 식사모임 (참여의향 4점)
  장벽: 이동 어려움
  개선: "모임 장소까지 이동할 수 있도록 차량을 지원해 주면 참여하기가 훨씬 수월할 것 같습니다."
```

"차량 지원"처럼 제가 보기에 넣지 않았던 표현이 주관식에서 반복해 나오면,
그게 바로 **실제 설문지에 추가해야 할 보기**입니다. 이 도구의 목적이 정확히 이것입니다.

## 기술적으로 신경 쓴 세 가지

### 1. 페르소나 요약을 LLM에게 맡기지 않았다

처음엔 "이 사람의 프로필을 자연스럽게 요약해줘"를 LLM에 시키려 했습니다. 그런데 이러면
데이터에 없는 정보가 섞입니다. 나이와 가구형태만 줬는데 "당뇨를 앓고 있으며 우울감이 있는" 같은
문장이 만들어지고, 그 위에서 설문을 돌리면 결과가 데이터가 아니라 AI의 상상에 기대게 됩니다.

그래서 페르소나 요약은 **규칙 기반 템플릿**으로 생성합니다.

- 입력 필드에 없는 정보는 만들지 않는다
- 진단명·성격·감정 상태를 추가하지 않는다
- "불쌍하다", "취약하다" 같은 가치 판단 표현을 쓰지 않는다

같은 이유로, 복지 관련 속성(이동 불편, 돌봄 필요)을 임의 확률로 만들지 않고
사용자가 입력한 교차표만 씁니다.

```
IF 80세 이상 AND 독거
THEN 이동불편 = 낮음 20% / 중간 35% / 높음 45%
```

### 2. 모델 응답을 그대로 믿지 않는다

LLM은 JSON만 달라고 해도 설명을 붙이거나 보기에 없는 값을 씁니다. 그래서 검증 단계를 넣었습니다.

1. 코드펜스나 앞뒤 설명이 섞여 있어도 **중괄호 균형을 맞춰 첫 JSON 객체만 추출**
2. 문항별로 검증 — 단일선택은 보기 안에 있는지, 척도는 1~5 정수인지, 복수선택은 최대 개수를 넘지 않는지
3. 보기와 미세하게 다르면(공백·부분일치) 근접 매칭으로 교정
4. 조건부 문항은 앞 문항 응답을 보고 필요한 경우만 요구
5. 실패하면 **오류 내용을 프롬프트에 붙여 최대 2회 재요청**, 그래도 안 되면 원문을 남긴 채 실패로 기록

배치가 중간에 끊겨도 성공한 응답은 유지되고, **실패한 것만 골라 다시 실행**할 수 있습니다.

### 3. 결과가 달라졌을 때 원인을 찾을 수 있어야 한다

같은 설문을 다시 돌렸는데 결과가 다르면, 모델이 바뀐 건지 설문을 고친 건지 패널이 바뀐 건지
알 수 없으면 아무 의미가 없습니다. 그래서 실행마다 다음을 스냅샷으로 저장합니다.

모델명 · temperature · System Prompt 원문 · 프롬프트 템플릿 버전 · 설문 버전 · 데이터셋 버전 · 세그먼트 조건

여기에 더해, 이미 실행된 설문을 수정하면 **자동으로 새 버전(v2)** 이 만들어지고
기존 응답은 예전 버전을 그대로 유지합니다. 패널 생성도 seed를 고정하면 항상 같은 결과가 나옵니다.

반복 실행 기능도 넣었습니다. 같은 설문을 2~3회 돌려 문항별 변동폭을 보여줍니다.

```
병원동행   31% / 28% / 33%   변동폭 5%p
스마트폰   22% / 24% / 20%   변동폭 4%p
```

변동폭이 큰 문항은 그 결과를 단독 근거로 쓰면 안 된다는 뜻입니다.

## 여러 모델을 갈아 끼울 수 있게

Provider 어댑터 패턴으로 만들어서 Mock / Google Gemini / Anthropic Claude / OpenAI 호환 API를
설정에서 고를 수 있습니다. 핵심 로직은 인터페이스 하나에만 의존하므로,
새 모델을 붙일 때 파일 하나만 추가하면 됩니다.

```ts
interface LLMProvider {
  isReady(): boolean;
  generateResponse(input: SurveyPromptInput): Promise<LLMRawResult>;
}
```

붙이면서 배운 것도 있습니다.

- **모델명은 추측하면 안 된다.** 제가 쓰려던 모델명이 실제로 있는지 확신할 수 없어서
  "내 API 키로 쓸 수 있는 모델 목록 불러오기" 버튼을 만들었는데, 계정에서 41개가 조회됐습니다.
  목록에서 고르는 게 확실합니다. 목록에 없는 이름은 직접 입력할 수도 있게 했습니다.
- **대량 호출에서는 추론(thinking)을 끄는 게 낫다.** 설문 응답은 단순·반복 작업이라
  내부 추론을 끄니 응답 시간이 8.9초에서 5.1초로 줄었습니다. 비용도 같이 줄어듭니다.
- **일시적 과부하(503)는 실패가 아니다.** 신형 모델은 요청이 몰리면 503을 반환합니다.
  자동으로 재시도하고, 그래도 안 되면 그 건만 나중에 이어서 실행할 수 있게 처리했습니다.

## API 키 없이도 돌아간다

남에게 보여줄 때 "API 키부터 발급받으세요"라고 하면 대부분 거기서 멈춥니다.
그래서 키가 하나도 없으면 자동으로 **데모 모드**로 동작하게 했습니다.

- 비용이 들지 않는 Mock(더미) 엔진이 응답을 만듭니다
- 같은 조건이면 항상 같은 결과가 나옵니다
- 화면·분석·비교 리포트는 실제 모델을 쓸 때와 **똑같이** 동작합니다

첫 화면의 버튼 하나로 가상 이용자 30명 · 설문 6문항 · 실행 결과 · 비교 리포트까지 만들어집니다.

```bash
git clone https://github.com/kijung4290/virtual-survey-lab.git
cd virtual-survey-lab
npm install
cp .env.example .env
npm run db:push
npm run dev
```

http://localhost:3000 에서 **「1분 만에 체험하기」** 를 누르면 됩니다.

## 이 도구가 하지 않는 것

만들면서 가장 오래 고민한 부분입니다. 기능을 넣지 않기로 한 목록이 기능 목록보다 중요합니다.

- 실제 사례관리 대상자의 개인정보를 입력받지 않습니다
- AI 결과를 **대상자 선정**에 쓰지 않습니다
- AI 결과로 **위험도 판정이나 개입 우선순위**를 정하지 않습니다
- 실제 주민의 의견을 Synthetic 결과로 **대체하지 않습니다**
- 의료·정신건강·학대·위기 상황을 판단하지 않습니다
- 공식 통계 추정치나 대표성을 주장하지 않습니다

안전장치도 코드에 넣었습니다. CSV를 올릴 때 이름·전화번호·주소·주민등록번호·이메일로 보이는
컬럼이 있으면 가져오기를 차단하고, 값에서 주민번호·휴대폰 패턴이 발견되면 경고합니다.
물론 컬럼명을 바꾸면 우회할 수 있으니 **완전한 보호 장치가 아니라는 안내도 같이** 띄웁니다.

모든 데이터는 내 컴퓨터의 로컬 SQLite에만 저장되고, 특히 **실제 조사 결과는 외부 AI로 전송하지 않습니다.**
API 키는 서버 환경변수로만 읽고 DB에 저장하지 않습니다.

## 한계

정직하게 적어 둡니다.

- **이 결과가 실제 주민 응답과 얼마나 일치하는지는 아직 검증되지 않았습니다.**
  그래서 실제 조사 결과와 비교하는 기능을 넣었습니다. 쓸수록 이 도구가 얼마나 믿을 만한지 데이터가 쌓입니다.
- 합성 페르소나에는 복지 특성이 없는 경우가 많아, 그 부분은 사용자가 통계 분포로 채워야 합니다.
  즉 **입력한 통계의 품질이 결과의 상한**입니다.
- 주관식 분석은 v1에서 빈도 기반 키워드 수준입니다.
- 현재 구조(로컬 SQLite + 서버 내 배치)는 로컬이나 상시 실행 서버에 적합합니다.
  서버리스에 올리려면 DB와 작업 큐를 바꿔야 합니다.
